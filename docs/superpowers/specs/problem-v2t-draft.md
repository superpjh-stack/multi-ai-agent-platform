# 문제 정의 — 멀티 에이전트 대시보드

> 개정: 2차-T (2026-10-21) — F16 · §4.2b G17 · §5 · Q17~Q19 추가. 기능 명세는 `spec.md` v0.4.
> 개정: 2차-A (2026-10-20) — §2.3 · §4.2 · §4.3 · §5 · §8 Q9 · Q11~Q16 추가 · 수정. 1차(v1) 내용은 그대로 두었다.

## 1. 배경

2026-08 부터 스마트공장 사업 산출물(분석 · 설계 · 화면 · 시험 · 관리 문서)과 회사별 시스템(Data Gateway · Data Platform · MES · AI Platform · ML AI)을 Claude Code 에이전트로 만들고 있다. 작업 방식은 세 겹이다.

1. **프로젝트 세션** — 폴더 하나에 세션 하나 이상. 파이프라인 에이전트(`00 PM Agent` ~ `08 AI Agent Making Agent`)와 회사별 · 표준 플랫폼 저장소가 각각 세션을 갖는다.
2. **서브에이전트 · 포크 · 워크플로** — 세션이 일을 쪼개 백그라운드 에이전트를 띄운다. 한 세션이 서브에이전트를 60 개 넘게 띄운 경우도 있다(`Standard ML Platform` 64, `Standard MES Platform` 51, `SongWol QR Platform` 44 `[실측]`).
3. **자율 실행** — `/loop` · `ScheduleWakeup`(218 회) · 백그라운드 세션 · 세션 간 `SendMessage`(95 회)로 사람 없이 몇 시간씩 돈다.

에이전트는 늘었지만 **보는 눈은 터미널 탭 하나씩**이다. Claude Code 는 필요한 기록을 이미 다 남긴다 — 살아 있는 세션의 상태(`sessions/<pid>.json` 의 `status: busy|idle`), 대화와 도구 호출, 메시지마다의 토큰 사용량(`message.usage`), 서브에이전트의 유형 · 설명 · 깊이(`.meta.json`). 이것을 모아 보여 주는 화면이 없을 뿐이다.

## 2. 현재 문제

### 2.1 운영 중 드러난 문제

| # | 문제 | 근거 | 영향 |
|---|---|---|---|
| F1 | 실행 중인 에이전트 전체를 한 번에 볼 수 없다 | 백그라운드 서브에이전트 · 워크플로 에이전트는 터미널 탭이 없다. 대화형 세션도 탭을 하나씩 열어야 한다 | 몇 개가 동시에 도는지, 무엇을 하는지 모른다 |
| F2 | "대기"의 이유가 구분되지 않는다 | 입력 대기 · 권한 승인 대기 · `ScheduleWakeup` 으로 잠듦 · 백그라운드 자식 대기가 화면상 같다 | 내 답을 기다리며 멈춘 세션을 몇 시간 방치한다 |
| F3 | 부모 ↔ 자식 관계가 파일 안에 숨어 있다 | 자식 `.meta.json` 의 `toolUseId` 와 부모 `.jsonl` 의 `tool_use.id` 를 맞춰야 이어진다. 워크플로 에이전트는 `subagents/workflows/wf_*/` 아래 따로 있다 | "이 에이전트는 누가 왜 띄웠나" 를 추적하기 어렵다 |
| F4 | 세션 간 협업이 보이지 않는다 | `SendMessage` 95 회가 각 세션 기록에 흩어져 있다 | 어느 세션이 어느 세션에 일을 넘겼는지 그림이 없다 |
| F5 | 작업량 · 비용을 모른다 | 토큰은 메시지마다 `usage` 에 있지만 합산하는 곳이 없다. 캐시 읽기가 입력의 대부분이다(`Standard ML Platform` 입력 측 24억 토큰 대비 출력 242만 `[실측]`) | 어느 에이전트 · 프로젝트가 많이 썼는지, 캐시가 잘 먹는지 판단할 수 없다 |
| F6 | 멈춤과 끝남을 구분하지 못한다 | 프로세스가 죽거나 서브에이전트가 결과를 안 넘기고 끝나도 기록 파일은 그대로 남는다 | 끝난 줄 알았던 일이 반쯤만 되어 있다 |
| F7 | 파이프라인 진척이 `progress.md` 에만 있다 | 분석 → 설계 → 화면 → 시험 → 관리 산출물이 회사마다 폴더별 `progress.md` 에 따로 적힌다 | 회사 × 단계 진척을 한 표로 볼 수 없다 |
| F8 | 과거 실행을 되짚기 어렵다 | 세션 77 개 · 서브에이전트 232 개(+ 워크플로) 기록이 프로젝트 41 개 폴더에 흩어져 있다 | "지난주 송월 QR 작업에서 어느 에이전트가 실패했나" 를 찾는 데 오래 걸린다 |

### 2.2 대시보드를 만들면서 생길 문제

| # | 문제 | 영향 |
|---|---|---|
| P1 | 기록 형식이 Claude Code 버전에 따라 바뀐다 | 파서가 깨지면 숫자가 틀린다. 모르는 필드는 무시하고, 필수 필드가 없으면 건너뛴 줄 수를 드러내야 한다 |
| P2 | 기록 파일이 크고 계속 자란다 | 매번 전체를 다시 읽으면 느리다. 파일별 읽은 위치(offset)를 기억하는 증분 파싱이 필요하다 |
| P3 | 대화 본문에 민감 정보가 있다 | 고객사 자료 · 경로 · 키가 섞여 있다. DB 에는 메타데이터와 숫자만 두고, 로컬호스트에서만 열어야 한다 |
| P4 | 상태가 기록만으로 확정되지 않는다 | `sessions/*.json` 은 살아 있는 프로세스에만 있고, 서브에이전트에는 상태 파일이 없다. 마지막 기록 시각 · 마지막 항목 종류로 추정해야 한다(오판 가능) |
| P5 | 대시보드가 원천을 건드리고 싶어진다 | 훅을 추가하다 기존 `PreToolUse` · `PostToolUse` · `Stop` 훅(이슈 자동 등록 등)을 망가뜨릴 수 있다. 훅은 기존 항목에 덧붙이기만 하고, 송신 스크립트는 항상 성공으로 끝나 Claude Code 를 막지 않는다 |
| P6 | 그래프가 너무 커진다 | 에이전트 300 개 이상을 한 번에 그리면 읽을 수 없다. 기간 · 프로젝트 · 상태 필터와 접기가 기본이어야 한다 |

## 3. 핵심 질문

1. 이 컴퓨터의 모든 에이전트(세션 · 서브에이전트 · 워크플로 에이전트)를 **하나의 모델**로 묶고, 각각의 **현재 상태**를 몇 초 안에 정확히 말할 수 있는가?
2. "대기"를 **이유별로**(입력 · 권한 · 잠듦 · 자식) 나눌 수 있는가? 내 행동이 필요한 것만 골라낼 수 있는가?
3. **누가 누구를 띄웠고 누구와 주고받았는지**를 기록만으로 끊김 없이 이을 수 있는가? 못 이은 것은 정직하게 "부모 미확인" 으로 남는가?
4. 에이전트 · 프로젝트 · 유형 · 모델별 **작업량**(토큰 · 도구 · 파일 · 시간)을 같은 지표로 잴 수 있는가?
5. 파이프라인 에이전트의 **회사 × 단계 진척**을 사람 입력 없이 보여 줄 수 있는가?
6. (2차-A) 기록이 틀린 숫자를 **기록값을 바꾸지 않고** 얼마나 틀렸는지 함께 보여 줄 수 있는가?
7. (2차-A) 정한 한도에 견줘 **지금 얼마나 썼는지 · 어디가 늘고 있는지 · 어디가 캐시를 못 쓰는지**를 한 화면에서 볼 수 있는가?
8. (2차-A) 내 차례가 오면 **화면을 보고 있지 않아도** 알 수 있는가 — 원천을 건드리지 않고?

### 4.2b 2차-T 목표 (디지털 트윈, 2026-10-21)

### 4.3 이후 목표 (범위 밖 · 방향만)
